# Prepared formal maintenance report

`GET /api/maintenance-report` is disabled unless `OUCHI_REPORTS_ENABLED=true`, billing configuration is a verified ledger with HTTPS Supabase URL, and a publishable key is configured. Production billing configuration additionally requires the existing Apple application/verification safeguards. This change sets no flag, creates no paid infrastructure and deploys nothing.

The caller sends its bearer, one UUID homeId and the app epoch it previously confirmed in `X-Ouchi-App-Epoch`. Auth verifies the exact token before session claims are used. The service client reads the current enrollment and selected-environment server ledger; free/expired rights never construct a household client. Household loading and final home-access recheck use the caller JWT plus existing RLS, never service privileges. Auth, epoch and ledger rights are rechecked after loading. A changed binding, lost membership or expired subscription discards the report. An unavailable service is retryable, not evidence of paid access.

The response is no-store, bounded to two million UTF-8 bytes and includes environment, confirmed purchase-account token and report. The report counts registered products/tasks, current overdue/today tasks and six months of recorded completions using Japan dates. It does not infer fault or safety. Basic records/history and export remain free.

The existing development report API is unchanged. Its legacy test-grant path is not accepted by the formal endpoint. Native/Web formal UI wiring and selected environment/epoch response validation are still required. Do not advertise a purchasable released report benefit until those connections, actual Apple entitlement tests and release verification are complete. Prepared unit tests cover disabled configuration, ambiguous requests, exact ledger scope, expiry/auth/epoch/membership changes and outages. Disposable Auth/PostgREST/ledger integration uses synthetic purchase seeds; it is not an Apple signature or production endpoint proof.

# Purchase retention and account deletion proposal

Status: reviewable proposal, not enabled. No production deletion, ownership transfer or Apple API mutation is authorized by this document.

## Proposed data boundary

On completed Ouchi account deletion, erase household records, files, memberships, invitations, device registrations, reminder preferences, recovery jobs, app sessions and enrollment identifiers. Erase the Ouchi user/epoch association in purchase ownership, transaction and renewal rows rather than retaining the old UUID indefinitely. A hash of an identifier is still linkable information and does not count as anonymous deletion.

Before implementing this proposal, inventory every foreign key, inbox, audit record, log and backup that can preserve that association. A migration must establish a single locking protocol for deletion, enrollment, purchase processing and recovery. A worker may report completion only after each required category has a durable acknowledgement. Failed or unconfirmed erasure stays pending and must not grant access to a new enrollment.

Developer payout/accounting records are a separate category. Do not automatically retain customer identifiers under a bookkeeping rationale. The operator must identify required fields, legal basis, duration and access controls before any exception is implemented or described in the privacy policy. Backup expiry and actual completion times also remain to be established.

Shared Supabase login is not deleted globally: other apps may rely on it. The release must explicitly define what constitutes the Ouchi account and prove that all associated Ouchi personal data is erased. Disabling enrollment alone is insufficient.

## Restoring after deletion

An explicit Restore action must authenticate the new Ouchi enrollment and obtain current StoreKit information. Pairing Apple's verified AppTransaction and purchase transaction by bundle, environment and appTransactionId establishes consistency, not authorization to transfer ownership. The new helper performs only that pairing and preserves the original account token.

Before a transfer route exists, implement and validate a fresh, server-bound device/user authorization protocol, single-use challenges, expiration, atomic consumption, concurrency control, and a policy for conflicting active ownership. A replayed pair of valid JWS strings must never transfer rights. Client-supplied device identifiers or a locally computed device hash alone do not authenticate the sender to the server. Missing appTransactionId, failed verification or conflicting ownership must leave rights unchanged and provide a recoverable user-facing result.

Apple supports resetting appAccountToken with the Set App Account Token endpoint. Do not call it until authorization and transfer policy are implemented. After an authorized update, fetch and verify fresh Apple data and confirm the new token before recording a new association. Failure between update and readback requires idempotent reconciliation; it cannot be treated as a successful purchase. Handle expiry, refunds and revocation from current verified status, not from the age or presence of a signed pair.

Late notifications for erased/unmapped enrollments must not recreate the old identity or automatically assign a new one. The handler must bound and verify inputs, avoid logging personal payloads, and use the documented unassociated-event policy. That policy and replay/deduplication lifecycle remain release gates.

## Required proof before enabling

- Isolated database migration: all identifier-bearing categories erased, another user's data preserved, old workers and old sessions cannot recreate enrollment.
- Authorized restoration: replay, two competing enrollments, duplicate requests, token update timeout, readback mismatch, expiry, refund, revocation and missing fields leave correct ownership.
- Actual Apple Sandbox: signed AppTransaction, transaction, token update/readback and restore across Web/native accounts.
- Native deletion UI: export, reauthentication, immediate deletion option, subscription management link, truthful pending/completed status and restart-safe local cleanup.
- Final operator policy: retained fields if any, legal basis, finite duration, backup handling, support and shared-account boundary.

## Restore assertion client data (prepared, no authorization route)

The billing-restore-client-data helper creates a cryptographically random32-byte server nonce with a bounded five-minute validity window and produces deterministic UTF-8 clientData bytes. It binds the live user, Auth session, enrollment epoch, request, server-associated attested key identifier, App ID, App Attest environment, purchase environment and a domain-separated digest of the exact signed AppTransaction/purchase pair. The verified pairing helper now returns that digest while preserving the original transaction account token. App Attest environment and purchase environment remain separate; one does not imply the other.

This helper validates structure, canonical encodings and time only. A client-supplied key identifier is NOT proof of a verified device. Generating a nonce is NOT single-use consumption. There is no challenge store, attestation registration/verifier, assertion endpoint, counter update, ownership transfer, Apple mutation or rights grant in this change. Before returning a challenge, a future route must verify live Auth/current enrollment, both Apple signatures/pairing, and the server-stored key association, then persist the exact challenge. At validation, reconstruct exact clientData from that stored scope, verify Apple's App Attest assertion and atomically consume nonce/counter. No client JSON fields alone can approve a transfer.

Local tests cover random nonce generation, deterministic ordering, binding changes to every identity/environment/pair field, malformed encodings, expiry extension and bounded proof bytes. They do not prove Apple attestation or authorize transfer. The actual device/server protocol, replay/concurrency store, approved conflict policy, verified Set App Account Token/readback reconciliation and signed Apple Sandbox remain required.

Official Apple DeviceCheck validation documentation was fetched on2026-10-11. It requires randomized one-time challenges, verified certificate/key association, assertion signature verification and increasing counters. Current documentation also requires checking validation category and bundle version in authenticator extensions. Do not silently omit these or trust client-supplied values in a future verifier. The Set App Account Token documentation confirms that updates apply to the current/subsequent renewal transactions rather than past renewals; verified fresh readback is mandatory before granting new enrollment rights.

References: [App Attest server validation](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server), [Attestation validation guide](https://developer.apple.com/documentation/devicecheck/attestation-object-validation-guide), [Set App Account Token](https://developer.apple.com/documentation/appstoreserverapi/set-app-account-token).

## Assertion verification prerequisite (prepared, no restore endpoint)

The new billing-app-attest-assertion helper verifies the cryptographic assertion against a previously registered, Apple-attested P-256 public key. It checks the stored user/epoch/key/App ID/environment against the stored challenge, matches the SHA256 X9.62 key identifier, reconstructs exact clientData, checks RP ID and an increasing unsigned 32-bit counter, and requires signed validationCategory/bundleVersion extensions approved by a server build policy. Development permits category3; production permits explicitly configured category2/TestFlight or category4/App Store. There are no defaults that accept arbitrary builds. The bounded CBOR reader refuses duplicate keys, indefinite sizes, unsupported types, malformed UTF-8, excessive depth/items, and trailing bytes. It preserves a leading Unicode BOM inside a text value rather than changing map-key identity.

ECDSA/SHA256 verification takes the derived nonce as its message. An independently published historical assertion fixture confirms that mode; a preimage-message signature is refused. That historical fixture has no current required build extensions and is NOT accepted as a complete current assertion. Local generated P-256 fixtures exercise scope/signature tampering, wrong keys and environments, counter replay, expiry and malformed encodings. They are synthetic cryptographic tests, not Apple certificate validation or signed Apple Sandbox proof.

This pure helper deliberately does not persist or consume anything. Checking the same assertion twice against an unchanged stored counter produces the same result; the future database transaction MUST compare-and-swap the expected previous counter and consume the unique stored challenge exactly once. A successful crypto result alone MUST NOT grant rights. There is still no certificate/receipt verifier or key registration, live Auth/enrollment route, persistent one-use ledger, device integration, approved transfer policy, Apple token mutation or purchase access grant. No production database change or purchase activation is included. Registration verification, actual current-device extension compatibility, atomic replay/concurrency handling, deletion of future challenge/key rows and signed Apple Sandbox remain release gates.

Independent signature-mode reference: [node-app-attest implementation and public fixture](https://github.com/uebelack/node-app-attest). Apple requirements remain governed by the official references above.

## Persistent challenge consumption (prepared migration, no production apply)

The subsequent restore-challenge-ledger migration adds private RLS key/challenge tables and a service-only atomic consumer. Registration and challenge insertion pin the common account advisory lock and require an already mapped, live explicit enrollment. A challenge stores its exact scope, five-minute expiry, nonce and canonical clientData digest. The consumer rechecks live Auth/enrollment, locks the registered key and challenge in order, compares the expected previous counter, and updates counter/consumption together. Replays, stale counters, expired challenges and wrong session/scope return false. No browser role can register, inspect or consume these rows.

The consumer is NOT a signature verifier: the future server route must first run the crypto helper using trusted stored inputs and pass its result to the CAS. There is no key-registration endpoint/certificate or receipt validation yet, so only synthetic isolated fixtures register keys. There is no transfer job or Apple mutation. A lost consumption acknowledgement must not grant rights or automatically retry a transfer; a durable authorized transfer job and reconciliation must be designed before activation. Direct service-role access is trusted backend infrastructure, never a client capability.

Deletion removes all retained key generations and their cascading challenges under the current closed-account lease, after inventory/record/receipt prerequisites. Identity erasure and completed-receipt acknowledgement additionally require both new categories to be absent. The worker now waits for this stage. Local SQL tests cover live scope, expiry, stale-counter refusal, repeats, browser denial and foreign-user preservation. Disposable actual Auth/PostgreSQL integration tests exercise two concurrent consumer calls and retained-proof erasure; test fixtures remain explicitly synthetic and cannot prove Apple attestation or purchase transfer. A bounded service-only cleaner physically removes expired challenges without resetting counters; its scheduler is not activated. Key/receipt retention policy, attestation validation, route/device wiring and signed Sandbox remain incomplete release requirements.

## Attestation certificate prerequisite (no key registration)

The new billing-app-attest-certificate helper pins the SHA256 fingerprint of the Apple App Attestation Root CA published by Apple Private PKI. It verifies the two provided certificate signatures/issuer links, CA roles, root self-signature, certificate validity and P-256 credential key. It rejects additional/trailing certificate bytes, extracts the nonce only from the actual TBSCertificate extension sequence for OID1.2.840.113635.100.8.2, rejects duplicate OIDs and malformed DER, and compares that nonce with SHA256(authData || SHA256(stored registration clientData)). Caller input is the rebuilt 32-byte clientData hash, not a device-selected value. A root change requires reviewed code; no arbitrary trust-store or downloaded-root fallback exists.

The public Apple validation-guide fixture checked2026-10-11 is inconsistent with its stated SHA256-challenge calculation: its certificate nonce matches SHA256(authData || raw example challenge), while the documented SHA256-challenge calculation differs. Tests record and REFUSE that mismatch instead of accepting a second, weaker mode. The certificate also expired2026-04-23. An independent MIT-licensed historical public fixture verifies the pinned Apple signatures and the documented nonce calculation; its certificate expired2025-01-08. Neither proves a current device or Apple Sandbox. Source URLs and the independent fixture license accompany the test data.

This is a certificate/nonce prerequisite, not full App Attest registration. It does not consume a registration challenge, authenticate the user, enforce complete certificate-purpose/critical-extension policy, validate authenticator RP ID/counter/aaguid/credential/COSE/signed build extensions, or independently verify the receipt. In the current Apple guide the attestation validation category is encoded as four bytes; actual current-device assertion encoding and build-extension compatibility must be proven before activation. There is still no registration endpoint or production database write. All remaining checks and actual device/Sandbox proof are mandatory before persisting a trusted key or granting access.

Official certificate source: [Apple Private PKI](https://www.apple.com/certificateauthority/private/). Official fixture: [Attestation Object Validation Guide](https://developer.apple.com/documentation/devicecheck/attestation-object-validation-guide). Independent historical fixture: [node-app-attest attestation tests](https://github.com/uebelack/node-app-attest/tree/main/test/fixtures).

## Authenticator prerequisite and composed validation (no registration)

The authenticator helper now binds the expected App ID/RP hash, zero initial counter, exact environment aaguid, 32-byte credential identifier and the certificate-derived P-256 public key. A specialized bounded COSE prefix reader accepts the exact EC2/P-256/ES256 five-field key and requires its coordinates to match the certificate. Numeric/negative COSE labels do not become accepted in the string-key assertion decoder. The remaining bytes must contain the required signed build-extension dictionary; duplicate keys, malformed/truncated or trailing data fail. The Apple guide's actual category encoding is a four-byte little-endian byte string, validated without string/scalar coercion. Customer-app policy permits explicitly configured category3/development or category2/TestFlight and category4/App Store, with exact approved build versions. The guide's category1/OS fixture is refused as a customer app.

The composed prerequisite helper passes the SAME authenticator bytes and certificate-derived public key through both checks, preventing an authenticator-only mutation from bypassing the certificate nonce. Tests deliberately change the category/environment for authenticator-stage synthetic fixtures; those mutations do NOT constitute Apple proof and the composed verifier refuses the altered nonce. All documented mismatches remain failures. No client-supplied public key can substitute for the certificate-derived key in the composed path.

Complete certificate purpose/critical-extension policy, independent receipt validation, live enrollment and one-use registration challenge consumption remain required before registering a key. Current-device build-extension and assertion-format compatibility also remain unverified. The composed result contains a receipt TO VERIFY, not a verified receipt or permission to register/restore. There is no new endpoint, database activation or purchase grant. A full current Apple attestation success must be proven with an actual device; historical or synthetic stage tests are insufficient.

## Independent initial receipt verification (prepared, no device registration)

The subsequent receipt helpers independently authenticate the observed Apple App Attest PKCS7/CMS receipt format: ECDSA/SHA256, a single issuer/serial-selected signer, no signed/unsigned attributes, and a pinned public Apple Root CA G3 chain. This root is distinct from the private App Attestation root used for the credential certificate. Current public samples from Apple and the independent MIT-licensed fixture both pass signature verification at their historical certificate-valid dates. Unsupported algorithms, additional signers/attributes, untrusted/extra certificates, modified content, malformed BER/EOC/lengths, excessive nesting and trailing bytes fail closed. This is a constrained supported-format verifier; new formats require explicit implementation and tests rather than a signature bypass. It uses Node crypto, with no runtime shell or additional dependency.

The initial ATTEST receipt validator parses the payload, refuses duplicate attributes and unsupported attribute versions, verifies its signature, and requires the exact expected app, credential certificate/key and stored challenge SHA256. Creation time cannot be in the future or more than five minutes old; expiration must be finite and still future. The signed creation time selects certificate validation time, following Apple's receipt guidance. An untrusted preparse may select that time but never authenticates a receipt; the exact payload still has to pass cryptographic verification and scope checks. Refreshed RECEIPT types are not accepted as initial registration. The public Apple guide fixture's raw24-byte challenge field is refused instead of weakening the expected32-byte hash match. The independent historical fixture passes all initial-receipt binding checks at its signed creation time; both fixtures are stale now and cannot register a current device.

The registration-proofs composer derives receipt expectations from the SAME certificate and stored challenge used by the authenticator prerequisites. It does not accept a device-selected public key/hash as a substitute. Complete certificate-purpose/critical-extension policy, live Auth/enrollment, a persisted one-use REGISTRATION challenge and atomic key registration remain release gates. Neither composer writes the database or grants purchase rights. Actual current-device receipts and complete end-to-end attestation, fraud-metric refresh/receipt retention and Apple Sandbox still require verification before activation.

Sources checked2026-10-12: [Assessing fraud risk and verifying the receipt](https://developer.apple.com/documentation/devicecheck/assessing-fraud-risk), [Apple public PKI roots](https://www.apple.com/certificateauthority/), [Receipt certificate verification time](https://developer.apple.com/documentation/appstorereceipts/validating-receipts-on-the-device). Local public fixtures preserve their original source/license notices.

## Constrained certificate-purpose policy (prepared, no registration)

Both credential and receipt signature paths now apply the same bounded certificate-policy checker after pinned-chain signature validation. It refuses duplicate extensions, BER indefinite certificate structures, malformed critical flags, missing critical Basic Constraints/Key Usage, unknown critical extensions, CA/leaf-role mismatch, insufficient CA path length and inappropriate signing usage. Only understood Basic Constraints, Key Usage and validated EKU restrictions can be critical. Arbitrary recognized-by-name extensions are not silently ignored as critical policy.

The credential role requires the signed App Attest nonce-purpose OID1.2.840.113635.100.8.2. The current Apple public fixture additionally carries EKU1.2.840.113635.100.4.24; when present, that exact single purpose is required. The independently verified older Apple-issued fixture has no EKU, so the observed older profile still requires the signed nonce marker without inventing an undocumented mandatory EKU. Both profiles require the same private pinned chain, nonce/key binding, live challenge and authenticator checks. Other EKU restrictions fail closed.

For the observed receipt profile, the leaf must be the Apple-issued Application Attestation Fraud Receipt Signing subject and carry the signed purpose marker OID1.2.840.113635.100.12.15 containing DER NULL. The intermediate must match the observed Apple Application Integration CA5-G1 profile; the credential intermediate must match Apple App Attestation CA1. These subject/purpose checks supplement pinned-root signatures; names alone are never trusted. A different issuer/profile requires explicit review and tests, not a system-root fallback. Public fixture mutations in tests invalidate their signatures and are used ONLY to prove policy rejection, never as positive Apple proof.

This implements a constrained supported-profile policy, not universal X509 acceptance or proof of current-device compatibility. Revocation/fraud-refresh operations, live Auth/enrollment, one-use REGISTRATION challenge consumption, atomic key persistence and actual current-device/Sandbox validation remain release work. No endpoint, registry write, shared-database apply or rights grant is enabled. Source evidence is the signed public certificate metadata accompanying the Apple validation guide and independent fixtures, together with the official Apple PKI repository; optional/new certificate formats remain unapproved until verified.

## Purpose-separated registration challenge (prepared, not consumed)

The server-only registration challenge helper generates a random32-byte nonce with an exact five-minute lifetime and binds the user, authenticated session, enrollment epoch, request ID, key ID, app ID and App Attest environment. Its exact twelve-field schema and `register_ouchi_attested_key` purpose are distinct from purchase restoration; neither serializer accepts the other's challenge. Canonical UTF8 bytes are rebuilt in a fixed order from the SERVER-STORED record and SHA256 hashed for Apple's `attestKey` clientDataHash. Client transport key ordering cannot change the signed bytes. Unknown fields, noncanonical identifiers/nonces, extended lifetime, future or expired records fail closed.

The stored-challenge proof composer derives both the expected scope and SHA256 together and passes them to the certificate/authenticator/receipt validators. It does not accept an independently submitted hash. Tests bind every identity/app/key/environment/time field, reject cross-purpose substitution and prove that a public Apple attestation for a different challenge is refused. There is no current-device positive registration claim.

This is only construction and cryptographic composition. A REGISTRATION-specific persisted ledger, live Auth/enrollment checks before issue and at commit, atomic one-time consume plus globally unique key ownership, pruning/erasure, native challenge transport and current-device proof are still mandatory before activation. The existing RESTORE ledger must not be reused as registration authorization. No endpoint, shared-database migration, key write, purchase grant or real charge is enabled by this change. ## Registration ledger and atomic key commit (prepared, not activated)

The new additive migration stores REGISTRATION challenges in a separate private RLS table with no browser grants, a unique random nonce and exact five-minute lifetime. Its insertion trigger checks live explicit enrollment under the common account lock, the exact twelve-field schema, identity/app/key/environment binding and canonical nonce/time representations. It reconstructs the same fixed-order UTF8 bytes as the TypeScript helper and independently computes their SHA256 with PostgreSQL's built-in binary hash function. A supplied arbitrary hash is refused. No pgcrypto extension or external transaction call is needed.

The service-only commit RPC locks account, challenge and global key ownership, rechecks enrollment and the wall clock after lock waits, and requires exact stored client hash plus a key identifier matching SHA256 of the supplied X9.62 point. The trusted caller MUST already have cryptographically validated the certificate/authenticator/receipt for that exact stored challenge; a syntactically valid digest or byte array is not Apple proof. Key insertion and challenge consumption occur in one transaction. Another challenge cannot reuse an existing key or overwrite another account's ownership. An exact acknowledgement retry only reads back the same persisted proof, point, receipt, app and session within the live challenge; it never resets the assertion counter or inserts again. Legacy privileged key insertion remains present for migration/testing; production route wiring must use the verified atomic commit path.

A bounded service-only expiry prune physically removes expired registration requests without resetting registered keys. It is not scheduled yet. Account proof erasure now removes registration requests across retained epochs, and identity/checkpoint/completion predicates all require their absence. Unrelated owners' requests and shared Auth remain outside that erasure.

Local PGlite tests execute the actual new migration and validate canonical hash binding, wrong scope/proof/point refusal, global ownership, exact acknowledgement retry without counter reset, expiry/prune, revoked enrollment, browser denial and owner-only erasure. This local live-scope fixture is NOT real Auth or concurrency proof. The disposable real Auth/PostgREST workflow is extended to run concurrent registration requests, exact retry, changed proof, browser denial and a revoked real session; its result must be inspected before claiming those checks passed. The Apple point/receipt in these SQL tests are explicitly synthetic; no Apple device, Sandbox purchase or grant is claimed.

Official Supabase RLS guidance and the2026-09-25 PostgreSQL breaking-change notice were reviewed; this migration uses no ltree, legacy PGP cipher, float gist index or custom operator. Shared database apply, endpoint/native activation, current-device proof, scheduled cleanup and retention approval remain release gates. No real charge or production data mutation has been enabled.

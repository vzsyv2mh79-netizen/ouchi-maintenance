# Prepared formal reminder preferences

GET/PUT /api/reminder-settings is held unless OUCHI_REMINDER_SETTINGS_ENABLED=true and billingConfiguration returns a verified ledger configuration accepted by the strict HTTPS/Supabase deployment guard. Production also requires the existing Apple verification settings. No flag is enabled by this change. Settings persistence does not start a scheduler, send APNs/Web Push, or make a premium feature purchasable.

Requests carry the exact bearer and X-Ouchi-App-Epoch previously confirmed by the client. Auth verifies the exact bearer before signed session claims are read. Store RPCs use the verified user/session/enrollment and configured Sandbox or Production environment; the client cannot choose environment or paid status. The handler re-verifies Auth and current enrollment after the RPC before returning a binding-specific no-store response. Wrong enrollment refuses reads/writes. A failed or stale acknowledgement is not evidence that a write rolled back; clients must read or retry the same revision/value. Existing SQL already locks account access, checks server-ledger rights, enforces revision conflicts and acknowledges identical retries.

Reading expired/free preferences remains available to the scoped account. Saved preferences remain retained while effective settings revert to the free daily 09:00 Japan schedule. New custom writes require current paid rights in SQL. Account erasure still removes only matching closed-enrollment preferences using the validated worker lease; this route does not erase anything. The development endpoint retains Sandbox defaults and its original response shape.

## Daily identity across registration replacement

The prepared formal start path atomically reserves one destination/Japan-day identity before marking a send started. The SHA-256 input includes APNs environment, fixed topic and device token; purchase environment is deliberately excluded, so changing purchase configuration cannot bypass a destination's daily limit. The guard carries exact enrollment/job/lease ownership and survives cascading deletion of jobs during session replacement and explicit notification stop. It is personal data, not anonymous information, and raw tokens are not copied into this table. Concurrent conflicting reservations cannot both start. Accepted, unknown, aborted or otherwise unconfirmed starts remain fenced; only the trusted before-submission retry outcome releases the exact job/lease reservation. No legacy Sandbox dispatcher is enabled by this path.

Expiry is Japan midnight after the delivery day plus one further day (at most 48 hours from start); the bounded service-only cleanup deletes expired guards in batches of at most 500. This is a prepared cleanup function, not an enabled timer: coordinator cleanup with backlog monitoring must be connected and verified before release, so expiry alone is not proof that stored data was removed. The disabled deletion adapter also requires exact closed-enrollment/lease identity erasure before finalization. An explicit completed deletion removes that enrollment's guard; a fresh enrollment is a new consent boundary. Full deletion/retention and real device/Apple proof remain incomplete.


## Prepared resumable delivery coordinator

The native_delivery_sweep migration keeps at most four scope rows, keyed by independently fixed APNs/purchase environments. A 120-second lease serializes scans. Each invocation processes at most100 destinations through the existing job/identity guards and checkpoints a monotonically advancing cursor against the exact cycle, lease and previous cursor. An interrupted incomplete cycle resumes even when a new five-minute interval begins; a completed cycle waits five minutes and then starts from the beginning to include newly registered destinations. Japan midnight invalidates an old lease and starts a new cycle. Receipt loss does not justify resetting a stored cursor or resending a notification.

runStoredNativeDeliverySweep requires successful bounded expiry cleanup before dispatch and returns a cleanupBacklog signal when a full500-row batch was removed. Cleanup failure or changed coordinator scope/lease stops dispatch. The trusted route rechecks the sweep immediately before the APNs transport and uses independent bounded provider-receipt and checkpoint transports after execution cancellation. Stored job and daily identity guards remain the final duplicate fence if a sweep expires during a network operation.

## Same-day settings and expiry replanning

The formal scoped enqueue now updates an existing Japan-day job only when its effective schedule changed and submission definitely never started. Pending/skipped jobs or expired claims with no send_started_at may be requeued under the same job UUID with a fresh future lease. Active claims are not rewritten; their start/count guard refuses the changed schedule and a later scan may replan after a skipped acknowledgement. Lease, attempts and retry time are reset only for a changed effective schedule, and old acknowledgements cannot modify the new attempt.

Ordinary expiry/refund selects retained free09:00 daily defaults; an unsubmitted custom job can replan to those defaults once09:00 arrives. A future notification time or unselected weekday waits without overriding the current claim. A send already started, an accepted/unknown outcome, a failed terminal job or an existing destination/day identity never replans. There is still at most one actual submission per destination/Japan-day unless a trusted provider response proves no submission. Settings changes do not recall accepted messages. Legacy Sandbox daily enqueue retains its old behavior and remains separate from formal release scheduling.
